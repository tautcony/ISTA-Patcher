# ISTA Patch Maintenance

Methodology for deciding whether ISTA source/binary changes require updating
existing patches or adding new ones, and how to implement those changes in this
repo.

## Goal

Given a **new or updated ISTA version** (decompiled sources + optional genuine
binaries), produce a clear answer:

1. Which existing patches still apply (hit)?
2. Which patches miss (target moved / signature changed / body strategy broken)?
3. Which new license / integrity / feature-guard paths need new patches?
4. Concrete code changes in `ISTAlter` with correct attributes and verification.

Do **not** invent patches from speculation. Ground every change in decompiled
source and/or IL of genuine assemblies.

## Data Sources

| Role | Typical path | Contents |
|------|--------------|----------|
| Multi-version decompile (primary audit tree) | `../ista-test-data/<ver>-project/` | dnSpy/ILSpy-style C# projects per assembly |
| Genuine install trees | `../ista-test-data/<ver>_genuine/`, `../ista-test-data/<ver>/` | Real `TesterGUI/bin/Release/*.dll|exe`, PSdZ host, backups |
| In-repo reference decompile | `ref/<ver>-project/` | Same layout as ista-test-data projects; currently e.g. `4.58.12-project` |
| Patcher implementation | `src/ISTAlter/Core/PatchUtils*.cs` | All built-in patches |
| Patch orchestration | `src/ISTAlter/Core/Patch.cs`, `Patcher/Provider/*` | Apply order, filters, file list |
| Helpers | `src/ISTAlter/Utils/DnlibUtils.cs`, `AttributeUtils.cs` | IL rewrites, attributes |
| Config custom patches | `CustomPatchDefinition` + `CustomPatchUtils` | Simple return/empty ops without code change |
| Integrity file list | `Ecu/enc_cne_1.prg` under install root | Which DLLs the product expects |

Resolve paths relative to this repo root. Prefer absolute paths when shelling.

Example layout:

```text
repos/
  ISTA-Patcher/                 # this repo
    ref/4.58.12-project/        # decompiled reference for a version
    src/ISTAlter/Core/          # patches live here
  ista-test-data/
    4.51.18-project/            # older decompile
    4.52.21-project/
    4.53.13-project/
    4.53.13_genuine/            # genuine tree (TesterGUI, PSdZ, …)
    4.56.30/                    # binaries-only snapshot
```

When both `ref/` and `ista-test-data/` exist for the same version, treat them as
the same kind of input; use whichever is newer/complete for that version.

## Patcher Architecture (map first)

```text
CLI/GUI options
  → IPatcherProvider (DefaultPatcherProvider / Toyota / Solicitation)
      loads PatchInfo list from PatchUtils methods via attribute reflection
  → Patch.PatchISTA
      file list: enc_cne_1.prg or TesterGUI/bin/Release scan
      per assembly: LoadModule → for each PatchInfo:
        IsVersionInRange + IsPatchApplicable(LibraryName)
        → Delegator(module)  // returns # of bodies that actually changed
      → SetPatchedMark + SaveModule (fails closed if stamp/consistency fail)
```

### Where patches live

| File | Role |
|------|------|

| `PatchUtils.Optional.cs` | Optional feature patches (ENET, finished-op, data-not-send, clamp, …) |
| `PatchUtils.Toyota.cs` | Toyota / industrial customer |
| `PatchUtils.ISTAVoltage.cs` | ISTA voltage-related |

| `PatchUtils.Binding.cs` | Consistency / stamp / title binding |
| `AttributeUtils.cs` | Patch category + `FromVersion` / `UntilVersion` / `LibraryName` |

Do **not** hand-edit members generated by `ISTgenerAtor` into `PatchUtils`.

### Patch method contract

Every built-in patch is:

```csharp
[SomePatchAttribute]                    // category → provider include rules
[LibraryName("Some.dll")]               // optional but required if version-gated
[FromVersion("4.56")]                   // inclusive lower bound (optional)
[UntilVersion("4.58")]                  // exclusive upper bound (optional)
public static int PatchSomething(ModuleDefMD module)
{
    return module.PatchFunction(
        "Full.Type.Name",
        "MethodName",
        "(ParamType1,ParamType2)ReturnType",
        DnlibUtils.ReturnTrueMethod      // or custom Action<MethodDef>
    );
}
```

- Return value = number of methods whose **IL body fingerprint changed**.
- `0` → treated as miss for that target (shows as `-` in CLI result string).
- Matching uses **exact** type full name + method name + signature string
  (`DnlibUtils.GetMethod` / `DescriptionOf`).

### Version range semantics

`module.Assembly.Version ∈ [FromVersion, UntilVersion)`

- Missing `FromVersion` → no lower bound.
- Missing `UntilVersion` → no upper bound.
- Version attributes **without** `LibraryName` log an error (library check still skipped).
- Version mismatch is **silent skip** (expected), not a hard failure.

Canonical relocation pattern (keep both methods):

```csharp
[ValidationPatch]
[LibraryName("ISTAGUI.exe")]
[UntilVersion("4.58")]
public static int PatchMainWindowViewModel(...) { /* old type */ }

[ValidationPatch]
[LibraryName("ISTAGUI.exe")]
[FromVersion("4.58")]
public static int PatchMainWindowViewModelService(...) { /* new type */ }
```

Real example: `CheckExpirationDate` moved from
`MainWindowViewModel` (≤4.53 sources) to `MainWindowViewModelService` (4.58+).

## Workflow: New Version Compatibility Audit

Use this as the default procedure for a new ISTA version `V_new` vs last known
good `V_old` (or vs current patch code).

### Phase 0 — Inventory inputs

1. Confirm decompile tree: `ista-test-data/V_new-project` or `ref/V_new-project`.
2. Confirm genuine tree if available: `*_genuine` / binary snapshot with
   `TesterGUI/bin/Release`.
3. Note assembly version(s) on key DLLs (FileVersion / `AssemblyVersion`) — patch
   gating uses `module.Assembly.Version`.
4. List current patches: all `public static int Patch*` in `PatchUtils*.cs` with
   their attributes, type, method, signature, library, version bounds.

Helper extract (run from repo root):

```bash
# Rough inventory of built-in patches
grep -nE '\[(Essential|Validation|.*Patch).*\]|public static int Patch|PatchFunction\(|PatchAsyncFunction\(|PatchGetter\(|FromVersion|UntilVersion|LibraryName' \
  src/ISTAlter/Core/PatchUtils*.cs
```

### Phase 1 — Mechanical target presence check

For **each** existing patch target `(library?, type, method, signature)`:

1. In decompile of `V_new`, search type + method name:

```bash
# Example: expiration check relocation
find ../ista-test-data/V_new-project -name '*.cs' | xargs grep -l 'CheckExpirationDate'
grep -RIn 'IsLicenseValid' ../ista-test-data/V_new-project --include='*.cs' | head
```

2. Classify each target:

| Status | Meaning | Action |
|--------|---------|--------|
| **HIT** | Same type/method/signature, behavior still needs patch | Keep; may still need body strategy update |
| **MOVED** | Logic exists under new type/method/library | Split with `UntilVersion` / `FromVersion` |
| **RENAMED** | Same role, new names | Update strings; version-gate if dual support |
| **SIGCHANGE** | Same name, different params/return | Update signature string; version-gate if dual |
| **BODYCHANGE** | Match still works for empty/return ops; complex IL ops may break | Re-read method; fix rewrite |
| **GONE** | No equivalent | Bound with `UntilVersion`; document removal |
| **NEW** | New guard / license / integrity path | Design new patch (Phase 3) |

3. Prefer **primary defining assembly** sources (e.g. `RheingoldCoreFramework/.../LicenseStatusChecker.cs`)
   over nested copies under other projects (decompile trees often duplicate types).

### Phase 2 — Semantic / behavior check

Presence alone is insufficient. For each **HIT** and **MOVED** target:

1. Read decompiled method body. Decide required effect still holds:

   | Intent | Typical IL strategy (`DnlibUtils`) |
   |--------|-------------------------------------|
   | Force allow / valid | `ReturnTrueMethod` / `ReturnZeroMethod` (status enums often 0=valid) |
   | Force deny off | `ReturnFalseMethod` |
   | No-op void check | `EmptyingMethod` |
   | Force constant | `ReturnUInt32Method` / `ReturnStringMethod` |
   | Surgical edit | Custom `Action<MethodDef>`: find opcodes, rewrite, `ReplaceWith` |
   | Async method | `PatchAsyncFunction` → rewrite `MoveNext` of state machine |
   | Property | `PatchGetter` |

2. For surgical patches, re-validate **anchors**:
   - `FindOperand` / `FindInstruction` full-name strings
   - Instruction counts / local variable assumptions
   - String literals (XML fragments, config keys)
   - Call site indices (e.g. second `apiInitExt` in ENET patch)

3. Flag **complex** patches for deeper IL verification on genuine DLLs when
   decompile is ambiguous (obfuscation, compiler differences).

### Phase 3 — Hunt for NEW guards (source-driven)

Do not only re-check old targets. Scan for new blocking logic in areas the
patcher already cares about:

Search themes in `V_new` decompile (and compare to `V_old`):

```text
License / activation:
  License, LicenseStatus, VerifyLicense, IsLicenseValid, Activation,
  Certificate, WhiteList, SecureAccess, IntegrityManager, VerifyStrongName,
  PackageValidity, Revocation, RSA, Signature

Environment / online:
  IsAvailable, Offline, iLean, MarketLanguage, UserEnvironment, LoginOptions,
  ClientConfiguration, Sync

Programming / FSC / brand:
  FSC, Swt, Fake, BrandCompatible, IndustrialCustomer, Toyota, ENET, ICOM

UI / lifecycle:
  CheckExpiration, SystemRequirements, FinishedOperation, ProgrammingSession

Data / telemetry:
  DataNotSend, FASTA, Telemetry, EdgeTelemetry, Multisession
```

Diff strategy when two project trees exist:

```bash
# High-signal: files that exist only in new version or changed around license
diff -rq ../ista-test-data/V_old-project/RheingoldCoreFramework \
         ../ista-test-data/V_new-project/RheingoldCoreFramework \
  | head -100

# Method-level: compare specific known files
diff -u \
  ../ista-test-data/V_old-project/ISTAGUI/BMW/Rheingold/ISTAGUI/ViewModels/MainWindowViewModel.cs \
  ../ista-test-data/V_new-project/ISTAGUI/BMW/Rheingold/ISTAGUI/ViewModels/MainWindowViewModel.cs
```

For each **new** gate: identify defining assembly → type → method → desired
forced outcome → optional flag category (essential vs validation vs optional).

### Phase 4 — Implement updates

#### 4a Update existing patch

1. Edit the relevant `PatchUtils*.cs` partial.
2. If dual-version support is required, **do not overwrite** the old method:
   add `UntilVersion` on old, new method with `FromVersion`.
3. Keep `LibraryName` accurate to the **module full name** of the file being
   patched (usually the DLL/EXE file name as loaded).
4. Preserve SPDX headers; follow file-scoped namespace / usings conventions.
5. BMW type name strings in code often use Unicode escapes for `BMW`
   (`\u0042\u004d\u0057`) — match existing style in the same file.

#### 4b Add new built-in patch

Checklist:

1. Choose category attribute (or add a new one in `AttributeUtils` + wire
   `DefaultPatcherProvider` / CLI option if user-facing).
2. Implement `public static int Patch…(ModuleDefMD module)`.
3. Prefer simple return/empty helpers; only hand-write IL when necessary.
4. For multi-target patches, sum return values of multiple `PatchFunction` calls.
5. Log `Log.Warning("Required instructions not found…")` and leave body
   unchanged when anchors missing — do not throw; return 0 via fingerprint.
6. Optional only: simple ops can be config `CustomPatchDefinition` instead of code.

#### 4c Signature construction

Signature format must match `DnlibUtils.DescriptionOf`:

```text
(param1FullName,param2FullName)returnFullName
```

Rules:

- No spaces after commas.
- Use **full** type names as dnlib reports them (`System.String`, not `string`).
- Generics: `System.Func`2<A,B>`, `System.Collections.Generic.Dictionary`2<K,V>`.
- Nested types: `Outer/Inner` if that is how dnlib names them (prefer reading
  from a real `MethodDef` when unsure).
- Modopts appear in some signatures (see historical `GetSubVersion` patch).

From decompiled C#:

```csharp
internal LicenseStatus IsLicenseValid(LicenseInfo testLicInfo, bool isid)
```

→ type `BMW.Rheingold.CoreFramework.LicenseManagement.LicenseStatusChecker`  
→ name `IsLicenseValid`  
→ desc `(BMW.Rheingold.CoreFramework.LicenseInfo,System.Boolean)BMW.Rheingold.CoreFramework.LicenseStatus`

When uncertain, load genuine DLL with a tiny dnlib snippet or temporary test and
print `DescriptionOf(method)`.

#### 4d Complex body rewrite pattern

```csharp
static void Rewrite(MethodDef method)
{
    var call = method.FindOperand<MemberRef>(OpCodes.Callvirt, "Full.Method.Name(...)");
    if (call == null)
    {
        Log.Warning("Required instructions not found, can not patch {Method}", method.FullName);
        return;
    }
    // mutate instructions or method.ReplaceWith([...]);
}
```

Anchors must be stable across the supported version range; if not, version-split
the patch.

### Phase 5 — Verify

#### 5a Unit / focused tests

```bash
dotnet test src/ISTestA/ISTestA.csproj --filter FullyQualifiedName~PatchUtils
```

Add or extend tests when changing version gating, library checks, or IL helpers
(`PatchUtilsHelperTests`, `PatchUtilsFingerprintTests`, `DnlibUtilsTests`).

#### 5b Dry-run on genuine tree

```bash
dotnet run --project src/ISTA-Patcher -- patch \
  --mode Standalone \
  --force \
  "/absolute/path/to/genuine-or-snapshot"
```

Interpret per-file result string:

- Hex digit → that patch index applied N times (fingerprint changed).
- `-` → not applied (wrong library/version, miss, or no body change).
- `[NOP]` → no patch applied to file.
- `[FNC: nn]` → success path; backup under `@ista-backup`, output `@ista-patched`.
- Summary line: `applied/attempted` patches and skipped count.

Re-run with optional flags as needed (`--enable-enet`, finished-op, etc.).

#### 5c Spot-check patched IL

Load `@ista-patched/Some.dll` in dnSpy/ILSpy or dnlib and confirm target methods
show the forced body. Confirm `PatchedAttribute` / mark present.

#### 5d Regression across versions

If supporting multiple major minors, re-run at least one older genuine tree
(`4.53.13_genuine`, etc.) to ensure `UntilVersion` splits did not break older
hits.

### Phase 6 — Record outcome

Produce a short audit note (comment, PR body, or `docs/` note) with:

- `V_old` → `V_new`
- Table: patch name | status | action
- New patches added
- Known residual risks (obfuscated assemblies, missing genuine tree, untested flags)

## Decision Tree (quick)

```text
New ISTA version available
  │
  ├─ Can find old targets with same sig?
  │    ├─ Yes, simple return/empty still correct → no code change
  │    ├─ Yes, but surgical anchors broken → fix rewrite / version-split
  │    └─ No
  │         ├─ Logic moved → new method + From/Until
  │         ├─ Logic removed → UntilVersion on old
  │         └─ Logic replaced by new design → new patch + retire old
  │
  └─ New license/integrity/online guards?
       ├─ Same category as existing → add sibling Patch* method
       └─ New product feature toggle → new attribute + CLI/GUI option if user-facing
```

## Common Failure Modes

| Symptom | Likely cause | Fix |
|---------|--------------|-----|
| Many `-` on expected DLL | Wrong `LibraryName` or version gate | Align attributes with assembly name/version |
| Method exists in source but patch returns 0 | Signature mismatch / wrong type full name | Print `DescriptionOf`; fix desc string |
| Patch "applies" but app still blocks | Wrong method or incomplete call chain | Trace callers in decompile; patch higher/lower |
| Works on 4.5x fails on 4.5y | Body-dependent surgical patch | Version-split; refresh anchors |
| Save discarded / no output | Stamp/consistency failed or verification | Check `SaveModule` / `Anchor` logs |
| `[VER: …]` skip | Already patched | Use `--force` or restore from `@ista-backup` |
| Nested type not found | Decompile path ≠ runtime assembly | Patch the assembly that actually ships the method |

## Encoding / Safety Notes

- This project patches third-party installs: always backup (`@ista-backup`); prefer
  writing to `@ista-patched` then validate before replacing originals (existing flow).
- Use `PathSafetyUtils` for any new path logic; never ad-hoc traversal checks.
- Do not log secrets, machine identifiers, volume serials, or full sensitive paths
  beyond existing diagnostics patterns.
- Cancel as `OperationCanceledException`; do not swallow in broad catches.
- Do not generate exploit payloads; only IL edits needed for the documented patch goals.

## Agent Execution Checklist

When invoked for a version audit, work in this order and report progress:

1. [ ] Identify `V_new` / `V_old` paths (ista-test-data + ref + genuine).
2. [ ] Inventory current patches and attributes.
3. [ ] Presence matrix (HIT/MOVED/SIGCHANGE/GONE) for all essential + validation patches.
4. [ ] Scan for NEW gates in license/integrity/UI paths.
5. [ ] Propose code changes (list methods/files) before large edits if ambiguous.
6. [ ] Implement patches + version gates.
7. [ ] `dotnet build` / focused tests.
8. [ ] Patch dry-run on genuine tree if available; paste summary counts.
9. [ ] Write status table of outcomes and residual risks.
